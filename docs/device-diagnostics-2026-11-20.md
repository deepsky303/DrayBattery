## Выключение Wolverine и повторное обнаружение

[ФАКТ] Для проверенного беспроводного подключения 1532:0A4C с точным дескриптором
`Razer Wolverine V3 Pro for Xbox 2.4` выключение геймпада убирает USB-функцию из
Windows. На проверенном порту это неотличимо от извлечения приёмника. Прежняя
обработка USB removal удаляет последний заряд и иконку.

Пользователь отверг сохранение значка при исчезнувшем USB-подключении: оно
оставляло бы тусклую запись также после физического извлечения приёмника.
Эта промежуточная политика удалена из кода. В окончательном варианте отсутствие
USB-подключения удаляет иконку, в том числе при ручном выключении данного геймпада.
Приёмник G903 остаётся видимым во сне мыши, поэтому её тусклая запись сохраняется.
Кэш модели не может создать новую запись.

При включении XInput/USB могут появиться до готовности HID-канала аккумулятора.
Для нового подключения добавлены четыре ограниченных повтора только battery GET
Wolverine через 3, 8, 16 и 30 секунд между попытками. Успешный ответ, исчезновение
подключения или исключение отменяют повторы; обычный периодический опрос не
перезапускает исчерпанную серию. Уведомление об изменении устройств может начать
новую серию для присутствующего Wolverine без показания. Частота аппаратных
запросов к устройствам других производителей из-за этой серии не увеличивается.

XInput создаёт виртуальный дочерний USB-узел `&IG_00` с тем же VID/PID. Список
повторов фильтруется по точному формату корневого USB-идентификатора: виртуальный
узел и `&MI_01` не считаются отдельными приёмниками. Это проверено на реальном
дереве PnP и регрессионным тестом отмены всех повторов после ответа корневого узла.

## Причина ошибки Mi и границы защиты

[ФАКТ] `BatteryLifecycle::Apply` вызывал `Invalidate` для отключённого Bluetooth-
контейнера даже до первого показания. Это создавало `invalidAfter_`, но не создавало
`windowsInvalid_`: сравнивать было не с чем. Проверка при последующем подключении
требовала наличие `windowsInvalid_` и поэтому бесконечно отклоняла первое показание.
Refresh запускал тот же алгоритм и не мог исправить состояние.

Новый регрессионный тест воспроизводит старт с отключёнными Mi, два снимка
присутствия и последующее подключение со 100%. На исходном коде тест падает на
проверке существования одной записи; после изменения проходит.

Исправление разрешает первое сохранённое показание только после положительного
подтверждения соединения конкретного Bluetooth-контейнера. Для ранее виденного
кэша сохраняется запрет повторного использования после отключения. Новая метка
обновления Windows разрешает тот же процент при повторном подключении; более
старая метка не может откатить уже принятое значение. При нескольких источниках
выбирается свойство с более новой меткой.

После уточнения пользователя исправлена также яркость: подтверждённое соединение
и доступное значение Windows отображаются обычной яркостью с пометкой `(Windows)`.
При исчезновении текущих данных последнее значение остаётся приглушённым.
Это не присваивает системному свойству статус прямого измерения: batteryCached
остаётся true, batteryFresh=false, lastLiveMs=0; индикация зарядки и новые
уведомления о низком заряде на основании кэша не включаются.
Сопряжение, сервисный дочерний узел или наличие радиомодуля
не заменяют положительный признак соединения корневого узла.
