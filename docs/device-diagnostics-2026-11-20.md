# DrayBattery: диагностика Mi Earphones 2 Pro и Wolverine, 20 ноября 2026

[ФАКТ] Проверка выполнена на авторизованном Draycos. Исходная версия — 0.1.12,
коммит `aba3228`, ветка `main`; два прежних неотслеживаемых файла результатов
не изменялись. Проект — C++17/Win32, MSVC 2022, отдельные тестовые программы.
Рабочая ветка — `fix/device-diagnostics-20261120`, резервная —
`backup/pre-device-diagnostics-20261120`. Установленный EXE скопирован отдельно;
его SHA-256 до и после проверки:
`6BCE2663C33B54A9271F0441D25761494730766696BE2E3751A051EC54834B20`.

## Подтверждённые наблюдения

- В Application Event Log за семь дней не найдено событий 1000/1001/1002/1026
  с именем приложения `DrayBattery.exe`. Доступные папки CrashDumps и WER
  ReportArchive/ReportQueue не содержали отчётов DrayBattery.
- До наших тестов последние остановки в lifecycle.log отмечены
  `EXIT_REQUEST(menu)` и `EXIT(normal)`. Есть отдельный `ENDSESSION` при завершении
  сеанса Windows. Это не устанавливает причину сообщённого пользователем вылета.
  Падения тестовых EXE по assert не являются падениями приложения.
- Пользователь подтвердил Mi Earphones 2 Pro. До подключения корневой Bluetooth-узел
  имел IsConnected=false; после подключения — true. На HFP-дочернем узле того же
  контейнера Windows сообщает 100% и FILETIME обновления свойства.
- Устройство с именем H600 Logitech Headset оставалось отключённым; его показания
  не использовались вместо Mi. Сопряжённые Xbox Bluetooth-контроллеры также были
  отключены, EDIFIER R1280DB подключён, свойства аккумулятора у него нет.
- Фактический Wolverine — USB `1532:0A4C`, дескриптор USB-родителя
  `Razer Wolverine V3 Pro for Xbox 2.4`, HID-интерфейс 1, feature report 91 байт,
  page/usage `0001:0000`. Это подтверждает Windows-режим текущего подключения;
  название «8K» само по себе не использовалось для выбора протокола.
- Драйвер игрового интерфейса — Microsoft xusb22.inf, 10.0.26100.9818;
  компонент Razer LWI — 2.3.0.809. Настройки и драйверы не изменялись.
- XInput slot 0 отвечает, BatteryType=WIRED, BatteryLevel=FULL. WGI для того же
  VID/PID возвращает 1000/1000. Эти данные не приняты за реальный процент Wolverine.
- Отдельный документированный HID battery GET дал корректные status/TID/class/
  command/length/checksum и 34%. Последующие штатные полные опросы дали 33%, затем
  32%. Использовались только запросы чтения аккумулятора, без GIP-окна,
  изменения режима, частоты опроса, профилей, вибрации или прошивки.

## Причина ошибки Mi и границы защиты

[ФАКТ] `BatteryLifecycle::Apply` вызывал `Invalidate` для отключённого Bluetooth-
контейнера даже до первого показания. Это создавало `invalidAfter_`, но не создавало
`windowsInvalid_`: сравнивать было не с чем. Проверка при последующем подключении
требовала наличие `windowsInvalid_` и поэтому бесконечно отклоняла первое показание.
Refresh запускал тот же алгоритм и не мог исправить состояние.

Новый регрессионный тест воспроизводит старт с отключёнными Mi, два снимка
присутствия и последующее подключение со 100%. На исходном коде тест падает на
проверке существования одной записи; после изменения проходит.

Исправление разрешает первое сохранённое показание только после положительного
подтверждения соединения конкретного Bluetooth-контейнера. Для ранее виденного
кэша сохраняется запрет повторного использования после отключения. Новая метка
обновления Windows разрешает тот же процент при повторном подключении; более
старая метка не может откатить уже принятое значение. При нескольких источниках
выбирается свойство с более новой меткой.

После уточнения пользователя исправлена также яркость: подтверждённое соединение
и доступное значение Windows отображаются обычной яркостью с пометкой `(Windows)`.
При исчезновении текущих данных последнее значение остаётся приглушённым.
Это не присваивает системному свойству статус прямого измерения: batteryCached
остаётся true, batteryFresh=false, lastLiveMs=0; индикация зарядки и новые
уведомления о низком заряде на основании кэша не включаются.
Сопряжение, сервисный дочерний узел или наличие радиомодуля
не заменяют положительный признак соединения корневого узла.

## Проверки

- `run-tests-msvc.cmd`: 14 тестовых программ, все прошли, код завершения 0.
  Проверены также прежние сценарии сна, удаления USB, старых поколений,
  неподключённых Bluetooth-узлов, одинаковых моделей и приоритета живого измерения.
- `build-msvc-staging.cmd`: успешно; прежнее предупреждение NOMINMAX в
  `wolverine_xbox.cpp` сохраняется. PDB подготовлен вместе с EXE.
- `git diff --check`: успешно.
- Полный `--list` при остановленном основном экземпляре показал Mi 100% (Windows,
  сохранённое значение), Wolverine 32% (HID), G915 X 84%; спящая G903 не дала
  начальное живое показание в этом запуске.
- Работающий интерфейс через `--status` подтвердил видимые гарнитуру, геймпад,
  клавиатуру и исправный виджет. После живого ответа G903 30% число видимых

- При работающем приложении `--list --wolverine-only` завершился кодом 2 до
  обращения к устройству. `--list --os-only` успешно показал Mi через Windows.
- Уточнение яркости проверено отдельно: обновлённый тест сначала падал на
  старом правиле `asleep=true`, затем все 14 тестовых программ прошли. Проверены
  обычная яркость Windows-показания, потеря свойства и восстановление того же
  значения без отключения, неопределённое соединение, подтверждённое отключение,
  отсутствие отката и мигания от запоздавшего снимка.
- Новая сборка с исправленной яркостью запущена намеренным перезапуском в 01:50:02
  (процесс 23460), из отдельной папки staging; ярлык тестовой версии обновлён.

  widget_alive=1. В журнале Mi: kind=2 pct=100 dim=0 link=2 cached=1.

  записала `BATTERY_REMOVE_CONNECTION kind=2`, после чего visible_headsets=0,

- В lifecycle.log добавлены отдельные события появления, приглушения,
  восстановления показаний и удаления, включая причину удаления; без имён,
  аппаратных идентификаторов и серийных номеров. `--status` показывает число

## Что осталось проверить

- Причина сообщённого вылета не установлена: в имеющихся журналах нет аварии
  приложения. Добавлена диагностика; исправление вылета не заявляется.
- Xbox-режим 1532:0A3F не переключался и не проверялся. Его старый модельный кэш
  в исходной 0.1.12 отключён; отдельный reader не обеспечивает автоматическую
  передачу проверенного показания в текущий жизненный цикл.
- При перезапуске процесса последний живой процент хранится только в памяти
  старого процесса. Если новое приложение запускается во время сна G903,
  нельзя заявлять прохождение сценария «живое показание → сон» в этом процессе.
  Для проверки пользовательского наблюдения оставлен один процесс без перезапуска
  и запущено наблюдение фактического состояния G HUB. Переход G903 в NOT_CONNECTED
  с сохранением индикатора затем подтверждён на железе (см. проверки выше).
- На момент проверки сна мыши Wolverine по-прежнему видим в XInput, приёмник
  присутствует, очередные штатные HID-опросы дают 30%. Эти факты сами по себе
  не доказывают физическое состояние питания контроллера за радиоприёмником.
- Изменение положения меню не входило в это исправление и не выполнялось.

## Безопасность и воспроизводимость

Журналы, исходный EXE, результаты и скрипт наблюдения хранятся локально вне Git.
Настройки USB/Bluetooth/аудио, сопряжения, драйверы и Explorer не изменялись.
Онлайн-база устройств не обновлялась. Основной `dist/DrayBattery.exe` и его
автозапуск не заменены; выполняется тестовая сборка. Публикация и push не выполнялись.

Основание проверки формата battery GET:
[исходный протокол wv3c](https://github.com/pascalfilippi/wv3c/blob/main/docs/protocol.md)
и [реализация battery GET](https://github.com/pascalfilippi/wv3c/blob/main/src/wolverine/info.py).
Факт ответа конкретного контроллера подтверждён локальной проверкой, не описанием проекта.
